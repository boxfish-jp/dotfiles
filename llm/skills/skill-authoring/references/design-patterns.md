# スキル設計パターン

`SKILL.md` が1エージェント・1ファイルで収まらないときの型。原型は [skill-design-patterns.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/core/skill-design-patterns.md)（Claude Code 前提の箇所は DSH 向けに置き換え済み）。当てはまる失敗モードが無いなら使わない。

## 索引

| 起きている失敗 | 使うパターン |
|---|---|
| 並列エージェントが同じ基礎事実を読み直す | 共有 ground truth の注入 |
| 対象外のファイルまで評価してしまう | 対象の事前フィルタ |
| 検出と修正が混ざって誤検出・誤修正になる | 検出のみの境界 |
| 入力種別ごとに解析手順が大きく違う | 入力ハンドラの dispatch |
| ラップする CLI の版で手順が変わる | ツールバージョン別のサブディレクトリ |
| 標準が長く、毎回読むと注意が薄れる | 二層の標準 |
| 統合か並列かを毎回勘で決める | 統合/並列の適応切り替え |
| 複数の root でどれが有効か分からない | discovery root の整理 |

## 共有 ground truth の注入

**失敗**: N 個のサブエージェントを並列に走らせると、各自が同じ基礎事実（ファイル一覧、ナビ構造、CLI コマンド、スキーマ）を独立に読む。読み取りが N 回、信頼すべき事実が N 系統、古い状態を見る機会も N 回になる。

**型**: オーケストレーターが基礎事実を1回だけ集め、同じ文字列を各サブエージェントのプロンプトにそのまま貼る。ファイルを参照させない（参照すると各自が読みに行く）。ブロックには、存在するものの一覧・現在のコマンドやエンドポイント・ドメイン実体・現在日付を入れる。必要な分だけに絞る。

## 対象の事前フィルタ

**失敗**: 複数のファイルをレビュー用エージェントに全部渡すと、対象外のファイルまで評価され、誤検出とコンテキスト浪費が起きる。

**型**: オーケストレーターが変更ファイルの一覧を取り、対象を絞ってから各エージェントに渡す。DSH のスキルには `paths:` のような自動起動の絞り込みが無いので、絞り込みは呼び出し側かプロンプトで行う。スキル側は「渡された対象だけを見る」と明記する。

## 検出のみの境界

**失敗**: 検出と修正を1つのスキルに入れると、誤検出をそのまま修正する失敗と、正しく検出して間違って直す失敗が混ざる。利用者の確認点も消える。

**型**: 検出のみに限定し、レポートを返す。修正は利用者が読んだ後の別操作にする。冒頭で「検出のみ。修正しない」と宣言し、書き込み・編集・commit をしない。自動修正が目的のスキル（codemod、依存更新）だけ例外で、書き込むことを明示し dry-run を持つ。

## 入力ハンドラの dispatch

**失敗**: 異質な入力（画像とテキスト、GitHub issue とモックアップ）を1つのスキルで受けると、本文が分岐で膨らむか、片方の入力に硬直する。

**型**: `inputs/` に種別ごとのハンドラを置き、`SKILL.md` は種別を聞いて該当ファイルを読ませるだけにする。分岐が5ステップ未満なら本文に直接書く。各ハンドラが100行を超えるあたりから効く。

## ツールバージョン別のサブディレクトリ

**失敗**: ラップする CLI がバージョン間で挙動を変えると、単一の手順が一部の利用者で壊れる。

**型**: `tool-versions/v1.21/apply-changes.md` のように版ごとの手順を置き、`SKILL.md` が実行時に版を検出して振り分ける。未知の版なら対応範囲を言って止まる。`my-skill-v2/` を併置しない。版は中身で分ける。

## 二層の標準

**失敗**: 1,000〜5,000語の標準を毎回読むと、トークンと注意が薄れる。

**型**: 短い規則（100〜300語、命令形で3〜5個）を `AGENTS.md` に置き、全文はスキルの `references/` に置いて、本文から開く条件を書く。DSH は `references/` を discovery しないので、カタログを汚さずに詳細を保持できる。要約は箇条書きだけに保ち、更新時は両方直す。

## 統合/並列の適応切り替え

**失敗**: 複数ファイルの評価で、1エージェントに全部見せるか（文脈横断できるが高い）、ファイルごとに並列化するか（安いが矛盾を見えない）を毎回勘で決める。

**型**: 先に合計トークンを見積もり、閾値未満なら統合、以上なら並列にする。閾値は `context_window - プロンプト - 応答バッファ` から決める。見積もりは `文字数/4` 程度で十分で、10% 外しても損失は小さい。

## discovery root の整理

**失敗**: 複数の root に同じ name のスキルを置くと、rank の値が小さい方だけがカタログに出て、どれが有効か分からなくなる。

**型**: DSH が見るのは `.dsh/skills`（100）、`.agents/skills`（200）、`customSkillDirs`（300）、`~/.dsh/skills`（400）、`~/.agents/skills`（500）。**値が小さいほど優先**され、敗者はモデルのカタログに出ない（警告は出るがモデルには届かない）。同じ name は1箇所だけに置く。複数 CLI と併用するなら、`.claude/skills` は `customSkillDirs` に足したときだけ見えることを踏まえて、実体を1箇所に決める。

## 関連
