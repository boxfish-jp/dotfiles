# State Reduction Review

## When to apply

使う:

- 状態・フィールドを減らせるかレビューするとき
- リファクタリング候補を挙動影響度で分類するとき

使わない:

- 状態設計そのもの（`state-design`）
- 実装後の一般的なレビュー（`review`）

## やること
対象が持つ変数・状態を減らせるかを検討し、減らせるものと減らせないものを挙動影響度で分類して示す。

- 状態保持者とフィールドを列挙し、数を出す（定数・static・getterは数えない）
- 各フィールドを①挙動差ゼロ／②テストは通るが保証が弱くなる／③機能・回避策を捨てるに分ける
- ①は等価性の理由、③は落ちるテスト名か失う機能を添える
- 削減量がほぼなく機能だけ失うものは候補から外す
- 合計の前後（フィールド数・行数）と、①だけでどこまで減るかを示す

## 表現の実験

表現の変更は、フィールドの削除とは別の削減手段として扱う。表現を変えたとき何が表現できなくなるかを見る。

境界が閉じているとは、境界で全入力を検証し、失敗経路が throw か Result で決まっていること。

- 複数フィールドの組み合わせは、1つの判別 union に畳めないか見る
- 例: `{ loading: boolean; data?: User; error?: Error }` は8状態を表現できるが、loading/success/error の3状態だけを合法とするなら、判別 union にすると3状態だけを表現できる
- 合法状態を列挙し、依頼者に確認する。確認できないなら、表現変更は採らず、保留として記録する
- 表現変更の価値は、消える不正な組み合わせの数で測る
- 表現変更のコスト（移行、境界の parse、API 変更）も候補の採否に含める
- 内側のドメイン型で不正な組み合わせを言えるなら、表現変更の候補にする。境界のDTOは parse 前提なら許容する
- 境界が閉じている場合だけ、内側で再検証しない。閉じていない、または parse の失敗経路が未定なら、防御を消す案は②として記録し、採らない

## 分類
- ① 等価変換のみ（重複した通知経路、派生できる値、常に偽のフラグ、二重保持）
- ② テストは通るが、防御・重複抑止・後始末・順序保証が弱くなる
- ③ テストが落ちる、または機能・通知・再試行を失う
- 同じ形のフィールドでもテストの有無でコストが違う。まとめて判断しない
- union の要素（状態値）を減らしてもフィールドは減らない。それはフィールド削減の対象外。別操作として、複数フィールドの組み合わせを判別 union に置き換えると1つに畳めることがある（「表現の実験」の対象）

## 出力
ID を振り、分類順に表で出す。各行に根拠（等価性／落ちるテスト名／失う機能）を付ける。
表現変更は、変更前の型→変更後の型、表現できなくなる不正な組み合わせの数、フィールド数の変化、コスト（移行・境界の parse・API 変更）を1行で示す。フィールドが減らない場合は別枠にする。採らない表現変更は保留として別に示す。

## 検証
- 調査中はリポジトリを書き換えない
- 変異を当てるならリポジトリ外の使い捨てコピーで、テストと型チェックを回す
- わざと壊す変異を1つ入れて、失敗を検出できることを先に確かめる
- 実行できない環境なら「未検証」と書く

## 実装するとき
- 対象は ID で確定させる
- 1項目ずつ変更→テスト→型チェック
- 削減効果がほぼなく機能だけ失うと分かった項目は、その場で外して報告する

## 完了条件

- 全フィールドを①〜③のどれかに分類した（定数・static・getterは除く）
- ①は等価性、③は落ちるテスト名か失う機能を添えた
- 表現変更は別枠で、型の前後・消える不正な組み合わせ・コストを示した
- 変異を当てた場合は検証結果を書き、実行できない場合は「未検証」と書いた
- 調査中にリポジトリを書き換えていない
