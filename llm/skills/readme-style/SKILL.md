# README Style

## 原則

READMEは、初めてこのリポジトリを使う人が「動かせるようになるまで」の文書。
仕様書・設計書・運用手順書ではない。

- 読者の行動が変わる情報だけを書く。
- 詳細な挙動はテストに書く。テスト名とアサーションを仕様にする。
- 上流（言語、フレームワーク、CLI、外部サービス）の仕様はREADMEに写さない。
  必要なら上流へリンクする。
- 破壊的挙動だけは例外。細かくてもREADMEに1行残す。
- 内部実装とテスト用フックは書かない。

## 残すもの

1. 概要（1〜2文）
   - 何をするリポジトリか。
   - 何を担当しないか（例: 本体はビルドしない）。
2. 動作環境
   - 箇条書き。体言止めか簡潔な普通体で書く。
   - 必須ランタイム、対応プラットフォーム、依存の所有関係、動作確認済みバージョン。
   - 「自明だから」で落とさない。特に依存を利用者が渡す場合は明記する。
3. 最小の使い方
   - input の追加と、最小の呼び出し。
   - コピペで動くこと。
4. 主要な引数・設定
   - 呼び出しに必要なものだけ表にする。
   - 全オプションを網羅しない。
5. 破壊的挙動
   - 上書き、移動、削除、バックアップ、マイグレーション。
   - 1行でよい。
6. 任意依存の例
   - 必須に見せない。プレースホルダと「例」を使う。

## 落とすもの

- 内部実装の説明
  - symlink の貼り方、stamp ファイル、derivation の構築方法、テンポラリファイル。
- 上流の仕様
  - 環境変数の既定値、CLI の合成順序、deep merge、`!!js` など。
  - 上流のドキュメントへリンクするか、何も書かない。
- テストで保証している細かい分岐
  - 設定の優先順位、重複排除、入力型の組み合わせ、失敗条件。
- 内部テスト用フック
  - `passthru` など。
- 設計判断・実装理由
  - なぜその構成にしたか、なぜその順序か。
- LICENSE ファイルがある場合のライセンス節
  - リポジトリ直下に `LICENSE` があるなら、README の節は必須ではない。
- 開発者向けの手順
  - 個別チェックの実行、CI の内部、リリース手順。
  - README ではなく CI か開発者向けドキュメントに置く。
- 重複する節
  - 「使い方」と「動作」が同じことを言っていないか。

## 動作環境の書き方

箇条書きで、次の4点を過不足なく。動作環境は体言止めか簡潔な普通体で書き、
ですますに揃えようとして冗長にしない。

- 必須ツール（例: Nix と flakes）
- 対応システム
- 依存を誰が用意するか（例: 本体は input ではなく利用者が渡す）
- 動作確認済みバージョン

```markdown
- Nix（flakes 環境）。
- `x86_64-linux` / `aarch64-linux` / `x86_64-darwin` / `aarch64-darwin`。
- `dsh` はこの flake の input ではなく、利用者が `bin/dsh` を持つ derivation として渡す。
- 動作確認済みの dsh は `0.2.0-rc.2`。
```

NG: 「Nix が必要」だけ書いて、対応システムや依存の所有関係を落とす。
NG: 上流の全要件をコピーする。
NG: 箇条書きまで「〜です。」に揃えて冗長にする。

## コード例の規約

- 登場する識別子は、その例の中で束縛するか、プレースホルダだと明示する。
  - OK: `dsh = myDsh;` + 「`myDsh` は利用者が用意した derivation に置き換える」
  - NG: `inputs.llm-agents` を使うのに input 宣言がない
- 任意依存をメインの例に直接書かない。例として出すなら
  「使う場合は input に追加」と添える。
- 例同士を矛盾させない。
  - `profiles` に `headless` を入れているのに「profiles に無ければ」と書かない。
- 動かない例を注意書きで補わない。例自体を消すか直す。
  - 管理対象で使えないコマンドを「そのまま渡る」とだけ書かない。
- システム固有の値を固定しない。
  - `x86_64-linux` を書くなら「例」と明示するか、現在のシステムを取得する。

## 文体

- 地の文はですます調。
  - NG: 「flake の input に追加する。」
  - OK: 「flake の input に追加します。」
- 箇条書きは体言止め・簡潔な普通体でよい。動作環境は特にそうする。
- コード例内のコメントは、簡潔な普通体でよい。
- 見出しは名詞句。文にしない。
- インラインコードと日本語の間は1スペース。
  - OK: `dsh` はこの flake ではビルドしません。
  - NG: dshはこのflakeではビルドしません。
- 英単語と日本語の間も1スペース。
  - OK: 「この flake が担当します」
  - NG: 「このflakeが担当します」
- 箇条書きの句点は揃える（全部付けるか、全部付けない）。
- 句点・読点の直前に空白を入れない。
  - OK: 「動作確認済みの dsh は `0.2.0-rc.2`。」
  - NG: 「動作確認済みの dsh は `0.2.0-rc.2` 。」
- 行末に空白を置かない。
- 1段落を長くしない。手順は箇条書きにする。

## 長さ

- 概要から最小の使い方までが、最初の1画面に収まるようにする。
- 節を増やす前に、テストや上流に移せないか考える。
- 同じ内容を「使い方」「動作」「設定」に分散させない。

## 仕様をテストへ移す

READMEから仕様を消すときは、次のどれかにする。

1. テストに移す
   - テスト名を仕様として読めるようにする。
   - 失敗するアサーションを1つ以上持たせる。
2. 上流の仕様として扱う
   - 上流ドキュメントへリンクする。READMEには書かない。
3. 利用者に不要と判断して消す
   - 本当に行動が変わらないか確認する。

READMEに残す仕様は「利用者が判断に使うもの」だけ。
実装の都合やテストの内部事情は残さない。

## レビュー checklist

- [ ] これは利用者が動かすために必要か
- [ ] これは上流の仕様ではないか
- [ ] これはテストで保証できる細かい仕様ではないか
- [ ] 破壊的挙動を落としていないか
- [ ] 例はコピペで動くか。未定義の識別子はないか
- [ ] 任意依存を必須に見せていないか
- [ ] 例同士が矛盾していないか
- [ ] リポジトリ名・URL・input 名は一致しているか
- [ ] 動作環境は必須ツール・対応システム・依存の所有・確認バージョンを含むか
- [ ] 地の文はですます調か。動作環境の箇条書きは体言止めで簡潔か
- [ ] コード・英単語の前後の空白は揃っているか
- [ ] 句点・読点の前に余計な空白がないか
- [ ] 末尾空白、閉じていないコードフェンスはないか
- [ ] 同じことを2つの節で言っていないか

## 削る判断の例

| 項目 | 判断 |
| --- | --- |
| Nix / flakes が必要 | 残す（動作環境） |
| 対応システム | 残す（動作環境） |
| 依存を利用者が渡す | 残す（動作環境） |
| 動作確認済みバージョン | 残す（動作環境） |
| 既存プロファイルのバックアップ | 残す（破壊的挙動） |
| 環境変数の既定値 | 落とす（上流の仕様） |
| 合成順序・deep merge | 落とす（上流の仕様） |
| `passthru` などのテスト用フック | 落とす（内部） |
| 設計判断・実装理由 | 落とす（テストやコードで表現する） |
| LICENSE ファイルがある場合のライセンス節 | 落とす（`LICENSE` で足りる） |
| 設定の細かい分岐・重複排除 | 落とす（テストへ） |
| 「動作」「検証」だけの節 | 落とす（重複・開発者向け） |
| 任意依存を直接使う例 | プレースホルダ＋注記に変える |
