# Testing Conventions

## When to apply

使う:

- テストを書く・追加する・見直すとき
- テスト名・group・ファイル構造を決めるとき

使わない:

- プロダクトコードのスタイル（`coding-style`）
- README の文面（`readme-style`）
- テストの実行や CI の設定

例はフレームワーク非依存の疑似コード。

## Test Naming Conventions

テスト名は**仕様ドキュメント**として読めるように書く。テストランナーの出力がそのまま仕様一覧になることを意識する。

### 文体（普通体／可能形）
- **仕様の記述** → 普通体（終止形 `〜する`）
  - `getUserNameの値を返す`
  - `不正な入力でArgumentErrorを投げる`
- **使い方・ユースケース** → 可能形（`〜できる`）
  - `switch文でパターンマッチできる`
  - `バイト列から復元できる`

### group 名
テストの主題（クラス名やメソッド名）で始める。

```
group('Payload')                    # クラス名
group('fromJson')                   # メソッド名
group('全フィールドに値が必要')      # クラス名を親groupで示せている場合
```

### コード参照と日本語の間のスペース
変数名・メソッド名・キーワードなどのコード参照の直後には**スペースを入れない**。

```
getUserNameの値を返す          # OK
getUserName の値を返す          # NG
```

### テストファイルの構造
1テストファイル＝1クラス（または1機能単位）。パッケージ構成を test/ 以下にミラーする。

### テストの構造化
テスト対象メソッドごとにテストを分ける。同一メソッドの成功・失敗テストは同じグループにまとめる。

```
# OK: メソッドごとにまとめている
GetUserName
├── 成功時にユーザー名を返す
└── engine例外時にNATIVE_GET_USERNAMEエラーを返す

# NG: 成功と失敗が別々の場所にある
OnMethodCall
├── GetUserName（成功のみ）
└── ...
OnMethodCallFailure
├── GetUserName（失敗のみ）
└── ...
```

### 失敗パスも書く
成功パスだけでなく、例外・エラーパスもテストする。各メソッドのtry/catchパスを網羅的にカバーする。

## 手順

1. テスト対象のメソッドごとに group を作る
2. 成功パスと失敗パスを列挙する
3. テスト名を仕様として書く
4. コード参照のスペースを確認する

## 出力

- テストコード（成功パスと失敗パス）
- テスト名・group名の一覧（必要な場合）

## 完了条件

- テスト名が仕様として読める（仕様は普通体、使い方は可能形）
- group名が主題（クラス名・メソッド名）で始まる
- 同じメソッドの成功・失敗テストが同じグループにある
- 失敗パス（例外・エラー）がテストされている
- コード参照の直後にスペースを入れていない
