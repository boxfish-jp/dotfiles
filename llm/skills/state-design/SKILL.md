# State Design

## When to apply

使う:

- 状態をどこに持つか、何を派生にするかを決める
- 非同期イベント・タイマーの状態を設計する
- ガード・防御・状態フィールドを消せるか決める
- 不正な組み合わせを表現できない型を設計する

使わない:

- レビュー手順・候補の分類（`state-reduction-review`）
- 構造・共有・距離・命名（`code-design`）

## 要素を消す基準

この節でいう要素は、状態フィールド、ガード、防御、購読など、状態や防御に関わる削除・置換の対象単位。関数・ファイルの削除は `code-design` のインライン化・間接参照の節で扱う。

差分は、要素を消したときに挙動・型・テストに現れる変化で、レビューの diff や patch のことではない。

要素を消したときに現れる差分で決める。距離を変える場合は `code-design` の「距離の実験」、表現を変える場合はこのスキルの「状態の表現」を見る。

- 差分はあるが、それが何であるかを言えないなら、消さずに確認する。既存の非対称なら `code-design` の「非対称」の節、そうでなければ要素が何を守っているか確認する
- 差分が出ないなら、その要素が守っている入力・状態を1つ言えるか確認する。言えるなら残す（テストされていないだけかもしれない）。言えないなら、消さずに確認する。参照がない場合だけ消す
- 差分が既存の表現で守られているなら、要素を消す
- 差分が意図した挙動で、まだ表現されていないなら、その要素を同じ挙動を保つ別の形に置き換えて消す
  - 理由も、その種類に合った表現（挙動ならテスト、制約なら型、意図なら名前か `coding-style` の1行 justification の範囲のコメント、政策なら呼び出し側）に移す。挙動が保てない、または理由が表現されないなら要素を残す
- 差分が意図しない挙動で、どこにも表現されていないなら、要素を残し、何が起きているか確認する

「守られている」は、その差分を対象にした既存のテスト・型・名前・呼び出し側があり、消した後も同じ種類の表現でその差分を保つこと（挙動ならテストか型、制約なら型、意図なら名前か `coding-style` の1行 justification の範囲のコメント、政策なら呼び出し側）。テストスイート全体が通るだけでは足りない。

「意図」は、いま残すべき挙動として正当化できること（要件・既存のテスト・利用者との合意）。

確認先は、依頼者（意図）、git log/blame、既存テスト、呼び出し側の grep。決められなければ依頼者に聞いて止まる。

たとえば、`isLoading` を消してスピナーが出なくなったなら、差分は挙動。スピナーの表示を、`isLoading` の値ではなく挙動としてテストし、`isLoading` を `status` union に置き換えられるか試す（`state-reduction-review` の「表現の実験」）。

ガードが制約なら、型・境界の parse・呼び出し側のいずれかで、元の条件全体（必須だけでなく非空など）を表現できないなら残す。

政策なら、その政策を呼び出し側が実際に強制しているか確認する。強制していなければ残す。

例えば apiKey の必須チェックは、型で非空まで表現できないなら残す（境界の定義は `state-reduction-review` の「表現の実験」）。

差分は1要素ずつ見る。実際に試すならリポジトリ外の使い捨てコピーで。

## 状態の判定は真実の源で行う

「状態は少なく」はそのままでは使えないスローガンで、入力の性質による判定に置き換える。

- 入力から計算できる値 → stateにしない（派生）
- 外部の非同期イベント（DOMアニメーション、ネットワーク）を追跡する値 → state + イベント駆動 + タイマ安全網以外に表現手段がない。定数時間からの経過時刻で完了を推定しない（イベントは遅延する・来ないことがある。時間は真理の源ではなく保険に格下げ）
- 「時間から状態を計算」の危険: 割り込み・リセットで軸がずれると写像が破綻する（例: 中断で進行が凍結したカウントダウンと、中断時刻を始点とする完了は同じ時間軸に乗らない）
- stateの個数はUIの物理インスタンス数で下限決定される。関数でラップしても総数は減らない。減らせるのはデッドフィールドと配線の重複のみ
- 表現を変えて不正な組み合わせを減らす場合は「状態の表現」を見る。詳細な分類・検証は `state-reduction-review` の「表現の実験」に従う

## 状態の表現

複数のフィールドで1つの状態を表しているなら、判別 union に畳めないか見る。合法状態を列挙し、不正な組み合わせを型で表現できなくする。

- 合法状態を列挙する。依頼者と合意できないなら変更しない
- 境界で入力を parse し、内側では再検証しない（境界が閉じている場合だけ）
- 表現変更の価値は、消える不正な組み合わせの数で測る
- 移行・境界の parse・API 変更のコストを添える
- 詳細な分類・検証は `state-reduction-review` の「表現の実験」に従う

## 出力

- 状態の持ち方、派生にする値、削除・保持する要素の一覧
- 各削除に、その要素が何を守っているかの根拠
- 表現変更は、変更前の型 → 変更後の型、合法状態、消える不正な組み合わせの数、コスト

## 完了条件

- 各要素の削除・保持に根拠を添えた
- 表現変更に合法状態・消える不正な組み合わせ・コストを添えた
- 確認できないものは依頼者に確認して止めた
- コードを変更した場合、テストと型チェックが通る。実行できない場合は「未検証」と書いた
