# Bad Code Issue

## When to apply

使う:

- バイブコーディングで見つけたコードの症状を `boxfish-jp/bad-code` に記録するとき
- 実際に AI に出した修正指示を残すとき

使わない:

- 各リポジトリの実際のタスク Issue（それはそのリポジトリで切る）
- `coding-style` の改善案を書くとき（Issue 登録段階では書かない）
- PR・コミットメッセージ・既存 Issue のコメント
- 一般のバグ・機能要望（`issue-style` を使う）

## 原則

- 1 Issue = 1 症状の**パターン**。同じパターンが複数箇所にあるなら1つにまとめる。失敗の型が違うなら分ける。
- 同じパターンが3箇所にあるときに、3つの Issue を立てない。1つの Issue の `## 場所` に3つ書く。
- 失敗した箇所の数だけ Issue を立てない。Issue は「スキルが学ぶべき失敗の型」の単位。
- タイトルにプログラム固有の名前（関数名・クラス名・モジュール名・ファイル名・業務用語・製品名）を入れない。言語・フレームワークの構文名はよい。ドメインは本文に書く。
- 同じパターンの既存 Issue があれば、新規を立てずに事例を追記する。
- `## 参照` に、コードがある repo と、症状が出ている状態の完全なコミットハッシュを必須で書く。ファイル/関数だけでは、コードが変わると追えなくなる。
- 書くのは、観測した症状、浅いコード、実際の指示、参照（repo と commit）だけ。
- 原因・推測・期待する振る舞い・影響・優先度・ラベル・一般化・改善案は書かない。
- この Issue は後で `coding-style` を改善する材料。改善案は Issue 登録段階では書かない。
- 後で Issue を読んだ人がプロンプトを組み直せるように、元の依頼、症状の出るコード、実際の指示を入れる。深い内部実装は必須ではない。
- `boxfish-jp/bad-code` は private。コードや会話を貼ってよいが、秘密情報は入れない。
- リポジトリは `boxfish-jp/bad-code`。

## 手順

1. 既存 Issue に同じパターンがないか検索する。あれば新規を立てず、事例を追記する。
2. 同じ症状のパターンが複数箇所にないか確認する。場所が違うだけなら1つにまとめる。失敗の型が違うなら分ける。
3. 症状が出ている状態のコミットハッシュを確認する（`git rev-parse HEAD`）。修正済みなら `git rev-parse <fix>^` で修正コミットの親を使う。未コミットなら、その状態をコミットしてから記録する。
4. タイトルをドメイン抜きの症状パターンで書く。
5. `## 症状` `## 場所` `## コード` `## 実際の指示` `## 参照` を書く。
6. コードを浅く整える。症状が見える最小の範囲にし、無関係な行は省略する。
7. 実際の指示を引用で残す。
8. 事実チェックを通す。原因・推測・評価・一般化・改善案を削る。

## タイトル

- 症状のパターンを1行。プログラム固有の名前（関数名・クラス名・モジュール名・ファイル名・業務用語・製品名）を入れない。
- 言語・フレームワークの構文名（`if`、`null`、`useEffect` など）は、そのパターンを表すなら使ってよい。
- 例: `条件分岐が3段ネストし、正常系が最下段にある`
- 例: `失敗が null で返り、呼び出し元でエラーと不在を区別できない`
- 例: `private メンバに _ が付いていない`
- 悪い: `handleRequest で if が3段ネストし、正常系が最下段にある`（関数名）
- 悪い: `注文一覧の取得で if が3段ネストしている`（業務用語）
- 悪い: `早期リターンのルールを追加する`（改善案）
- タイトルから関数名・業務用語を消しても症状が伝わるか確認する。伝わらないならドメインが残っている。
- 接頭辞は付けない。リポジトリ全体がこの記録用。

## 本文

```markdown
## 症状

<何をしようとしていたか（ドメインの文脈はここに書く）。何が、どの条件で起きたか。観測した事実だけ。同じパターンが複数箇所であったなら、その事実も書く。>

## 場所

<同じパターンが現れるファイル/関数をすべて列挙する。特定できなければ省略。行番号は使わない。>

## コード

<症状が見える代表例を1つ。言語のフェンス付き。同じパターンの別の場所を足すなら短く。無関係な行は省略。>

## 実際の指示

> <AIに実際に伝えた指示。長ければ要点だけ。>

## 参照

- repo: <owner>/<repo>
- commit: <症状が出ている状態の完全なSHA>
- fix_commit: <修正コミット。分かれば>
```

- `## 症状`: 事実だけ。原因・推測・評価を書かない。タイトルに書かなかったドメインの文脈はここに書く。
- `## 場所`: `## 参照` の commit 時点でのファイルと関数。同じパターンが複数箇所にあるならすべて列挙する。箇所ごとに Issue を分けない。行番号は使わない。
- `## コード`: 浅くてよい。関数のシグネチャと、症状の出る分岐・ループが見える程度。代表例を1つ。ファイル全体や深い型定義は、症状の理解に必要なら足す。不要なら貼らない。10〜30行を目安に、長ければ省略する。
- `## 実際の指示`: 提案ではなく、その時に実際に伝えた文の引用。「次はこうするべき」は書かない。
- `## 一般化` / `## スキルへの提案` / ルール文 / NG/OK例は書かない。それらは Issue を読んで `coding-style` を直すときに行う。
- 深い内部実装は任意。プロンプトを組み直せるなら、浅いコードで足りる。必要なら症状の理解に必要な範囲だけ足す。
- `## 参照`: 必須。`repo` はコードがあるリポジトリ（`bad-code` ではない）。`commit` は `## コード` の状態、つまり症状が出ている修正前の完全なSHA。修正後のコミットを書くと、悪いコードが残っていない。
- `fix_commit` は任意。修正コミットが分かるなら添える。PR/会話リンクも必要なら `## 参照` に足す。

## 例

タイトル: `条件分岐が3段ネストし、正常系が最下段にある`

````markdown
## 症状

注文一覧の取得処理を書かせたとき、`handleRequest` で `if` が3段ネストし、正常系が最下段にあった。同じセッションで `handleUserRequest` にも同じネストがあり、2箇所で出た。条件を追加するたびに内側へネストが増えていた。

## 場所

- `src/order_handler.ts` の `handleRequest`
- `src/user_handler.ts` の `handleUserRequest`

## コード

```ts
function handleRequest(req: Request) {
  if (req.ok) {
    if (req.user) {
      if (req.user.active) {
        return doWork(req);
      }
    }
  }
  return null;
}
```

## 実際の指示

> 失敗条件を先に return して、正常系のネストを下げて

## 参照

- repo: boxfish-jp/order-service
- commit: a1b2c3d4e5f60718293a4b5c6d7e8f9012345678
- fix_commit: b2c3d4e5f60718293a4b5c6d7e8f90123456789a
````

## 出力

```markdown
タイトル: <症状のパターンを1行（ドメイン名なし）>

## 症状

...

## 場所

...

## コード

...

## 実際の指示

> ...

## 参照

- repo: <owner>/<repo>
- commit: <症状が出ている状態の完全なSHA>
- fix_commit: <修正コミット。分かれば>
```

## 完了条件

- 1つの症状パターンに絞られている。同じパターンの複数箇所は1つの Issue にまとまっている
- タイトルがドメイン抜きの症状パターンで、関数名・クラス名・モジュール名・ファイル名・業務用語・製品名を含まない
- `## 症状` を読めば、どのプログラムの話か分かる
- 同じパターンの場所が `## 場所` に列挙されている（特定できなければ省略）
- `## コード` が症状の分かる代表例で、言語フェンス付き
- `## 実際の指示` が引用で残っている
- `## 参照` に repo と、症状が出ている状態の完全な commit ハッシュがある
- `commit` が修正前の状態を指している（修正後のコミットだけを書いていない）
- 原因・推測・期待・影響・一般化・改善案・優先度・ラベルが無い
- 行番号を使っていない
- Issue を読んでプロンプトを組み直せる
