# Implementation Review

実装後の差分に対して、次の5つを確認する。

対象は、ファイル名・クラス名・メソッド名・テスト名の4つ。2は名前そのものを、3と4はその名前が指すファイル・クラス・メソッド・テストの中身を見る。4対象すべてで2〜4を確認し、1つの対象だけ見て終わりにしない。状態を持つクラス・モジュールでは、5も確認する。

| 対象 | 2. 名前と実態 | 3. ドメイン混入 | 4. 完結性 |
| --- | --- | --- | --- |
| ファイル名 | ファイル名と中身の責務が一致するか | 別ドメインの語彙・購読・通知・排他を持たないか | ready/dispose、状態の真実が1箇所か、テスト |
| クラス名 | クラス名が何をするか1文で分かるか | 別ドメインの状態・イベント・判断を抱えていないか | 非同期開始の完了、dispose、状態の所有者、素通し |
| メソッド名 | 対象と操作が分かるか | 引数・戻り値・例外に別ドメインの型や文言が漏れていないか | 順序依存、素通し |
| テスト名 | 何を保証するか分かるか | 別ドメインの都合で組んでいないか | 失敗パス、dispose、再接続、同時実行 |

## 1. クラスの機能分割と状態削減

- メンバ変数が4つ以上あるなら、まず `state-reduction-review` でフィールドを棚卸しする。減らせない状態だけを残し、その上で機能を分けることを検討する。
- privateメソッドが3つ以上あるなら、機能を分けることを検討する。
- 状態を減らすだけで足りるなら、クラスを分けない。
- ただし、コードが小さく機能も少ないなら、責務を分ける必要はない。
- 分割する場合は、機能ごとにクラスを分ける。
- 確認: 追加・変更したクラスのフィールド数とprivateメソッド数を数える。フィールドが4つ以上なら `state-reduction-review` の表を作り、削減後のフィールド数で分けるか決める。privateメソッドが3つ以上なら分割を検討する。小さいクラスなら分けない。

## 2. 名前と実態

4対象それぞれの名前が、実装している仕事を指しているかを見る。

- ファイル名: 中身の主要なクラス/関数と同じ仕事を指しているか。
- クラス名: 「何をするか」が1文で分かるか。
- メソッド名: 「対象」と「操作」が分かるか。
- テスト名: 「何を保証するか」が分かるか。

全対象に共通:

- 名前が実態より広くないか（汎用名だが特定機能専用）。広い名前（`Manager`、`Helper`、`Util`、`ObsAudio` など）は、中に複数機能を抱えていないか確認する。
- 名前が実態より狭くないか（特定名だが汎用機構）。
- 別の比喩や過去の名前が残っていないか。
- 同名のパッケージ・型・概念と衝突していないか。
- 名前を1文で説明したとき、その1文がコードの仕事と一致するか。
- 命名規約（snake_caseなど）の遵守と、責務の一致は別問題として扱う。
- 例: `setMuted` が何をミュートするか分からないなら `setDesktopMuted` にする。`ObsAudioClient` のように接続と音声解釈が混ざる名前は、`ObsConnection` と音声状態のクラスに分ける。
- 確認: 各対象の責務を1文で書き、名前と一致するか見る。一致しなければ、改名するか機能を分ける。
- 各対象を、一致 / 部分一致（広い・狭い・比喩）/ 不一致で分類する。

## 3. ドメイン混入

4対象それぞれについて、別ドメインの知識が入っていないかを見る。

- ファイル: 知らなくてよい語彙を持っていないか（CLIオプション名、画面文言、HTTP、SQL、別サービスのモデル、通知チャンネルなど）。別ドメインのイベント購読、状態更新、リトライ、通知、排他制御を抱えていないか。
- クラス: 別ドメインの状態・イベント・ポリシー判断を抱えていないか。そのドメインの知識が呼び出し側に漏れていないか。
- メソッド: 引数・戻り値・例外に、別ドメインの型・語彙・文言が漏れていないか。
- テスト: 別ドメインの都合（CLI引数、画面文言、外部サービスの状態など）でセットアップ・検証していないか。

補足:

- 合成ルート（index.tsなど）の混在は許容する。ただし、ポリシー判断・通知文言・状態遷移まで持つ場合は指摘する。
- 単なる転送・境界のためのcallbackは混入と区別する。
- 各対象を、なし / あり（混入しているドメイン名）で分類する。

## 4. 完結性

4対象それぞれについて、単体で閉じているかを見る。

- ファイル: コンストラクタで始めた非同期処理の完了を待てるか（ready / start）。購読、タイマー、ソケット、ファイル監視をdisposeで閉じているか。テストがあるか。
- クラス: 開始した非同期処理の完了を待てるか。購読・タイマーをdisposeで閉じているか。状態の所有者が1つか。中継だけのクラスになっていないか。
- メソッド: 呼び出し側が順序や前提を知らないと壊れないか。1行の素通し、中継だけのメソッドになっていないか。
- テスト: 失敗パス、dispose、再接続、同時実行を見ているか。

全対象に共通:

- 状態の真実が1箇所か。同じ事実を別ファイルがコピーしていないか。
- 失敗が握りつぶされていないか。unhandled rejectionがないか。
- 既存の非対称は、理由を確認するまで意図とみなす。
- 「動いている」ことを一致の根拠にしない。
- 各対象を、○ / △（外に状態がある、呼び出し順に依存、素通しが残る）/ ×で分類する。

## 5. 状態削減

クラス・モジュールが状態（フィールド、モジュール変数）を持つ場合、`state-reduction-review` をロードし、フィールドを①挙動差ゼロ／②テスト保証に影響なし／③機能・回避策を捨てるに分類する。フィールドが4つ以上、同じ事実を二重に持つ疑いがある、または機能分割を検討しているときは必須。

- ①は等価性の理由、③は落ちるテスト名か失う機能を添える。
- 削減量がほぼなく機能だけ失うものは候補から外す。
- 合計の前後（フィールド数・行数）と、①だけでどこまで減るかを示す。
- 分類の詳細・出力・検証は `state-reduction-review` に従う。
