# Implementation Review

検出のみ。修正しない。指摘を返し、修正は依頼があった場合の別操作にする。

## When to apply

使う:

- 実装後の差分をレビューするとき
- 名前・ドメイン混入・完結性・状態削減を確認するとき

使わない:

- 設計判断そのもの（`code-design` / `state-design`）
- レビュー範囲の決定（`review-range`）
- 修正の実行（依頼があった場合の別操作）

## 対象と観点

対象は、ファイル名・モジュール名・クラス名・関数名・メソッド名・テスト名の6つ。2〜4は6対象すべてを見る。1はクラス・モジュールの分割、5は状態を持つ場合に確認する。1つの対象だけ見て終わりにしない。

| 対象 | 2. 名前と実態 | 3. ドメイン混入 | 4. 完結性 |
| --- | --- | --- | --- |
| ファイル名 | ファイル名と中身の責務が一致するか | 別ドメインの語彙・購読・通知・排他を持たないか | ready/dispose、状態の真実が1箇所か、テスト |
| モジュール名 | モジュール名と公開APIの責務が一致するか | 別ドメインの状態・イベント・判断を公開APIに漏らしていないか | 公開API、状態の所有者、dispose、テスト |
| クラス名 | クラス名が何をするか1文で分かるか | 別ドメインの状態・イベント・判断を抱えていないか | 非同期開始の完了、dispose、状態の所有者、素通し |
| 関数名 | 関数名が対象と操作を1文で説明するか | 引数・戻り値・例外・副作用に別ドメインの型や文言が漏れていないか | 呼び出し順への依存、失敗パス、素通し |
| メソッド名 | 対象と操作が分かるか | 引数・戻り値・例外に別ドメインの型や文言が漏れていないか | 順序依存、素通し |
| テスト名 | 何を保証するか分かるか | 別ドメインの都合で組んでいないか | 失敗パス、dispose、再接続、同時実行 |

## 1. クラス・モジュールの機能分割と状態削減

- フィールドが4つ以上あるなら、まず `state-reduction-review` でフィールドを棚卸しする。減らせない状態だけを残し、その上で機能を分けることを検討する。
- privateメソッドが3つ以上あるなら、機能を分けることを検討する。
- モジュールの公開APIが複数の責務を持つなら、モジュールを分けることを検討する。
- 状態を減らすだけで足りるなら、クラス・モジュールを分けない。
- ただし、コードが小さく機能も少ないなら、責務を分ける必要はない。
- 確認: 追加・変更したクラス・モジュールのフィールド数、privateメソッド数、公開APIの数を数える。フィールドが4つ以上なら `state-reduction-review` の表を作り、削減後のフィールド数で分けるか決める。privateメソッドが3つ以上なら分割を検討する。小さいクラス・モジュールなら分けない。

## 2. 名前と実態

6対象それぞれの名前が、実装している仕事を指しているかを見る。

- ファイル名: 中身の主要なクラス・関数・モジュールと同じ仕事を指しているか。
- モジュール名: 公開APIが提供する仕事を指しているか。
- クラス名: 「何をするか」が1文で分かるか。
- 関数名: 「対象」と「操作」が分かるか。
- メソッド名: 「対象」と「操作」が分かるか。
- テスト名: 「何を保証するか」が分かるか。

全対象に共通:

- 名前が実態より広くないか（汎用名だが特定機能専用）。広い名前（`Manager`、`Helper`、`Util`、`ObsAudio` など）は、中に複数機能を抱えていないか確認する。
- 名前が実態より狭くないか（特定名だが汎用機構）。
- 別の比喩や過去の名前が残っていないか。
- 同名のパッケージ・型・概念と衝突していないか。
- 名前を1文で説明したとき、その1文がコードの仕事と一致するか。
- 命名規約（snake_caseなど）の遵守と、責務の一致は別問題として扱う。
- 例: `setMuted` が何をミュートするか分からないなら `setDesktopMuted` にする。`ObsAudioClient` のように接続と音声解釈が混ざる名前は、`ObsConnection` と音声状態のクラスに分ける。
- 確認: 各対象の責務を1文で書き、名前と一致するか見る。一致しなければ、改名または分割を指摘する。
- 各対象を、一致 / 部分一致（広い・狭い・比喩）/ 不一致で分類する。

## 3. ドメイン混入

6対象それぞれについて、別ドメインの知識が入っていないかを見る。

- ファイル: 知らなくてよい語彙を持っていないか（CLIオプション名、画面文言、HTTP、SQL、別サービスのモデル、通知チャンネルなど）。別ドメインのイベント購読、状態更新、リトライ、通知、排他制御を抱えていないか。
- モジュール: 公開APIに別ドメインの型・イベント・ポリシー判断が漏れていないか。
- クラス: 別ドメインの状態・イベント・ポリシー判断を抱えていないか。そのドメインの知識が呼び出し側に漏れていないか。
- 関数: 引数・戻り値・例外・副作用に、別ドメインの型・語彙・文言が漏れていないか。
- メソッド: 引数・戻り値・例外に、別ドメインの型・語彙・文言が漏れていないか。
- テスト: 別ドメインの都合（CLI引数、画面文言、外部サービスの状態など）でセットアップ・検証していないか。

補足:

- 合成ルート（index.tsなど）の混在は許容する。ただし、ポリシー判断・通知文言・状態遷移まで持つ場合は指摘する。
- 単なる転送・境界のためのcallbackは混入と区別する。
- 各対象を、なし / あり（混入しているドメイン名）で分類する。

## 4. 完結性

6対象それぞれについて、単体で閉じているかを見る。

- ファイル: コンストラクタで始めた非同期処理の完了を待てるか（ready / start）。購読、タイマー、ソケット、ファイル監視をdisposeで閉じているか。テストがあるか。
- モジュール: 公開APIが状態の所有者を1つにしているか。購読・タイマーをdisposeで閉じているか。中継だけのモジュールになっていないか。テストがあるか。
- クラス: 開始した非同期処理の完了を待てるか。購読・タイマーをdisposeで閉じているか。状態の所有者が1つか。中継だけのクラスになっていないか。
- 関数: 呼び出し側が順序や前提を知らないと壊れないか。失敗を握りつぶさず、戻り値か例外で返しているか。1行の素通しになっていないか。
- メソッド: 呼び出し側が順序や前提を知らないと壊れないか。1行の素通し、中継だけのメソッドになっていないか。
- テスト: 失敗パス、dispose、再接続、同時実行を見ているか。

全対象に共通:

- 状態の真実が1箇所か。同じ事実を別ファイルがコピーしていないか。
- 失敗が握りつぶされていないか。unhandled rejectionがないか。
- 既存の非対称は、理由を確認するまで意図とみなす。
- 「動いている」ことを一致の根拠にしない。
- 各対象を、○ / △（外に状態がある、呼び出し順に依存、素通しが残る）/ ×で分類する。

## 5. 状態削減

クラス・モジュールが状態（フィールド、モジュール変数）を持つ場合、`state-reduction-review` をロードし、フィールドを①挙動差ゼロ／②テストは通るが保証が弱くなる／③機能・回避策を捨てるに分類する。フィールドが4つ以上、同じ事実を二重に持つ疑いがある、または機能分割を検討しているときは必須。

- ①は等価性の理由、③は落ちるテスト名か失う機能を添える。
- 削減量がほぼなく機能だけ失うものは候補から外す。
- 合計の前後（フィールド数・行数）と、①だけでどこまで減るかを示す。
- 分類の詳細・出力・検証は `state-reduction-review` に従う。

## 出力

対象ごとの分類表を出す。

```markdown
| 対象 | 名前と実態 | ドメイン混入 | 完結性 |
| --- | --- | --- | --- |
| ファイル名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
| モジュール名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
| クラス名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
| 関数名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
| メソッド名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
| テスト名: <name> | 一致 / 部分一致 / 不一致 | なし / あり（<domain>） | ○ / △ / × |
```

状態を持つ場合は、削減候補の表を別に出す。各指摘にはファイル・行・テスト名などの根拠を添える。

## 完了条件

- 6対象すべてを、2〜4の観点で分類した
- 状態を持つ場合、フィールドが4つ以上、同じ事実を二重に持つ疑いがある、または機能分割を検討している場合に `state-reduction-review` の表を作った
- 検出のみで、ファイルを書き換えていない
- 各指摘に根拠を添えた
- 設計判断が必要なものは `code-design` / `state-design` に渡した
