# Issue Style

バグは観測した事実だけ、機能要望・タスクは背景だけを書く。

## When to apply

使う:

- 新しい Issue のタイトルと本文を書くとき（バグ、機能要望、タスク）

使わない:

- 既存 Issue のトリアージ・コメント
- PR の文面
- 原因調査や修正案の作成（Issue には観測した事実だけを書く）

## 手順

1. open / closed の既存 Issue を検索する。重複なら新規を立てず、既存 Issue に事実を追記する。
2. 種別を決める。
   - バグ: 現状の振る舞いが意図と違うことを観測した。
   - 機能要望・タスク: 現状にはない変更を求める。バグではない。
   - 迷ったら、観測した失敗があるならバグ、なければ機能・タスク。1つの Issue に混ぜない。
3. タイトルを1行で書く。
4. 種別のテンプレートで本文を書く。
5. 事実チェックを通す。判断が混ざった文を、観測した事実だけの文に置き換えるか削る。
6. 出力する。

## タイトル

- バグ: 症状を1行。「〜のとき〜が〜しない」「〜すると〜になる」。原因・修正案を含めない。
- 機能要望・タスク: 求める変更を1行。「〜を追加する」「〜できるようにする」。実装方法は書かない。
- `バグ`、`動かない`、`改善`、`対応`だけにしない。
- 接頭辞（`[Bug]` など）はリポジトリの慣習に合わせる。無ければ付けない。

## 共通

- 見出しは指定のものだけ。テンプレがある場合は見出しを合わせる。
- 行番号は使わない（リファクタで壊れる）。
- 観測していないことは書かない。分からないことは「未確認」と書くか省略する。
- 因果語（〜が原因、〜だから、〜のせいで）を使わない。前後関係は事実として書く。
- 本文に「〜すべき」「〜が正しい」といった評価を書かない。

## バグ

本文は次の4節だけ。すべて観測した事実を書く。

- `## 症状`: 何が、どの条件で起きるか。件数・時刻・ID はそのまま書く。症状だけで異常だと分かるように具体的に書く。
- `## 再現条件`: 実行した操作、入力値、環境、再現率。第三者が同じ操作をできる粒度で書く。再現しなかった条件も事実なら書く。
- `## 場所`: 症状が現れるファイルと関数・節。特定できなければ省略する。
- `## 観測記録`: エラーメッセージ、ログ、スタックトレース、終了コード。テキストで書く。秘密情報はマスクする。無ければ省略する。

書かないもの: 原因、推測、期待する振る舞い、影響、修正案、テスト、前提、優先度、ラベル。原因が観測で確定していても書かない。修正の議論と PR に回す。

一般のバグテンプレートにある「期待する振る舞い」「影響」も書かない。判断はトリアージで行う。

## 機能要望・タスク

本文は `## 背景` だけ。

- 現状の事実を書く。何ができないか、そのとき何をしたか、どれだけ時間がかかったか、今どうしているか。
- 個人プロジェクトなので、賛同を得るための影響範囲・代替案・受け入れ条件は書かない。
- タイトルに求める変更を書き、本文には実装方法を書かない。

書かないもの: 解決策、実装案、期待する仕様、受け入れ条件、代替案、テスト、優先度、ラベル。

## 事実チェック

本文の各行を、観測した事実か判断かに分ける。判断が混ざったら、観測した事実だけの文に置き換えるか削る。

- 事実: 実行した操作、見た画面、出た文字、数、時刻、ID、バージョン、ファイル名、関数名。
- 判断: 原因、推測、期待、評価、影響、提案、優先度。

置き換えの例:

- NG: `config.Load` が nil を返すのが原因。
- OK: `config.Load` が nil を返した。
- NG: エラーメッセージを出すべき。
- OK: エラーメッセージは表示されなかった。
- NG: 設定不足で落ちる。
- OK: `config.yaml` が空のとき、終了コード 1 で終了した。
- NG: 全ユーザーに影響する。
- OK: 手元の 3 回の実行すべてで再現した。

## 例

バグの良い例:

```markdown
タイトル: config.yaml が空のとき CLI が exit 1 で終了する

## 症状

`config.yaml` を 0 バイトにして `app run` を実行すると、メッセージを出さずに終了コード 1 で終了する。手元では 3 回中 3 回再現した。

## 再現条件

1. `config.yaml` を 0 バイトにする
2. `app run` を実行する

- バージョン: `app 0.4.2`
- OS: Linux 6.12
- 2026-11-13 10:00 の実行で確認

## 場所

- `cmd/run.go` の `runCommand`
- `config.Load`

## 観測記録

`app run` の終了コードは 1。標準出力・標準エラーは空。
```

バグの悪い例:

```markdown
## 症状

設定の読み込みが原因で落ちている。おそらく nil チェック漏れ。

## 期待する振る舞い

エラーメッセージを出すべき。

## 影響

全ユーザーが使えない。
```

原因・推測・期待・影響が混ざっている。

機能要望・タスクの良い例:

```markdown
タイトル: CSV エクスポートに注文日の列を追加する

## 背景

現在の CSV エクスポートは注文 ID・商品名・金額の3列で、注文日は含まれていない。2026-11 の月次集計では、注文日を注文 ID から手で引き当てて 120 件を照合した。
```

機能要望・タスクの悪い例:

```markdown
## 背景

CSV に注文日が必要。

## 解決策

`orders.created_at` を YYYY-MM-DD で出力する。

## 受け入れ条件

- 注文日が含まれる
```

「必要」という判断、解決策、受け入れ条件が混ざっている。

## 出力

バグ:

```markdown
タイトル: <症状を1行>

## 症状

<観測した事実。件数・時刻・ID はそのまま>

## 再現条件

<操作、入力値、環境、再現率。すべて観測した事実>

## 場所

<ファイルと関数・節。特定できなければ省略>

## 観測記録

<エラー、ログ、終了コード。秘密情報はマスク。無ければ省略>
```

機能要望・タスク:

```markdown
タイトル: <求める変更を1行>

## 背景

<現状の事実。何ができないか、何をしたか、どれだけかかったか、今どうしているか>
```

ユーザーが明示的に別の項目を求めた場合だけ、その項目を追加する。

## 完了条件

- 種別がバグか機能要望・タスクか決まっている
- バグ: 症状・再現条件・場所・観測記録が観測した事実だけで、原因・推測・期待・影響・修正案・テスト・前提・優先度・ラベルが無い
- 機能要望・タスク: 本文が `## 背景` だけで、解決策・実装案・期待する仕様・受け入れ条件・代替案・テスト・優先度・ラベルが無い
- バグのタイトルが症状を1行で表し、原因・修正案・優先度を含まない
- 機能要望・タスクのタイトルが求める変更を1行で表し、実装方法・優先度を含まない
- すべての文が「観測した」か「現状の事実」として説明できる
- 行番号を使っていない
- 秘密情報をマスクしている
- テンプレがある場合、その見出しに合わせている。許可範囲外の欄はテンプレ側から削っている
